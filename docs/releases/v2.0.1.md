# AI OS v2.0.1

Status: prepared for review; publication is pending approval.

This patch improves native close recovery and project registration. A completed
close returns publication readback in the same call. Unknown Claude directories
can ask the user to choose a project and register through the existing journaled
writer. Read contention, missing admission, malformed command arguments and
malformed ledgers retain explicit, distinct refusal paths.

## Scope and compatibility

The canonical product version is `VERSION` (`2.0.1`), with intended tag `v2.0.1`.
The source manifest format `public-native-1`, semantic contract
`native-semantic-public-1`, event schemas and storage generation are unchanged.
The optional `attach_workspace` registration field is additive. No state migration,
automatic ledger repair, provider call or global harness reconfiguration is added.

Registration identity comes from validated argv. This public distribution uses
its existing ownership, shutdown and `recovery_only` controls; it has no separate
maintenance dispatcher. Stdin cannot select close/reconcile to bypass those checks.
The exact diagnostic command only discovers the source contract; it does not
inspect project ledger contents or establish runtime admission.

The missing-admission incident's original cause is unresolved. These changes repair
specific routing/recovery behavior; they do not establish a universal diagnosis.

## Install and upgrade

Fresh installations use the [technical guide](../setup-guides/native-bookkeeping-install.md).
The repeatable installer still refuses changed installed runtime bytes. This release
does not add an unattended upgrade command or authorize installing into any live system.

For an existing public installation, an operator must review a code-only upgrade
plan for that installation before applying it:

1. Close sessions, verify committed publication, and prevent new admissions during
   the change. Inspect pending journals and resolve them using the selected runtime.
2. Keep an exact backup and preimage SHA-256 inventory of the complete installed
   runtime, configuration, local instruction note and coordination specification.
   Preserve their permissions and the chosen Python executable/path.
3. Stage and test the complete v2.0.1 package separately. Compare every installed
   runtime file against its old manifest. Any unexplained edit stops the upgrade.
4. Under the installation's writer/maintenance exclusion, replace only reviewed
   code and instruction files whose preimages still match. Use the complete new
   runtime and matching manifest together. Update product-version metadata from
   `VERSION`; preserve project mappings, ownership and state paths. Merge the new
   close guidance into customized instructions without discarding local rules.
5. Run the installed doctor and verify version `2.0.1` and runtime integrity.
   Resume admissions only after fresh host SessionStart, checkpoint and close
   checks in every intended harness. Verify the closing receipt in the same call.

Do not copy an example configuration over a working installation. Do not reinstall
over live sessions, delete old journals or replace project ledgers/snapshots.
The installation-specific upgrade plan and real host checks remain operator work;
fixture validation is not evidence that an in-place deployment occurred.

## Rollback

Keep the prior complete runtime until acceptance. Stop admissions and finish or
reconcile pending publication before reverting code. Restore only files whose
current hashes still match the recorded upgrade postimages, retaining permissions
and using the old runtime with its matching old manifest. Inspect newer edits
instead of overwriting them. Reverse only the reviewed version/instruction edits.

Keep all new sessions, project rows, aliases, worktree mappings, snapshots and
journals. Never roll state back to an old backup. The storage contract is unchanged;
the previous runtime lacks the new conversational attachment/close guidance.
Verify doctor and fresh native host lifecycle checks again before continuing.

## Validation and limits

See [the validation record](../native-bookkeeping-validation.md) for the exact
tested tree, interpreter/platform results and extracted-artifact checks. Synthetic
fixtures exercise the public installer and entrypoint without provider calls.
Real Claude/Codex UI delivery remains a separate acceptance check. Windows-only
sharing and shell cases explicitly skip elsewhere. No universal host enforcement,
cross-machine coordination or full-system acceptance is claimed.
